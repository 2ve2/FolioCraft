# Authentication mail transport diagnosis and HTTP repair

Updated 2026-10-20. The HTTP repair is implemented locally; deployment and real provider acceptance remain pending human confirmation. No recipient address or credential belongs in this document.

## Evidence and lifetime
- **Verified in code:** `apps/api/src/lib/auth/index.ts` awaits `sendAuthMail` in both Better Auth callbacks and does not configure `advanced.backgroundTasks.handler`. `worker.ts` has no `ctx.waitUntil` integration.
- **Verified in installed code (Better Auth 1.7.7):** `dist/api/routes/password.mjs` awaits `runInBackgroundOrAwait(sendResetPassword(...))`. `dist/context/create-context.mjs` awaits the promise when no background handler exists, catches failures and logs them without rethrowing. Therefore a known-user reset normally waits for the mail attempt, yet can still return HTTP200/status:true when that attempt fails. Unknown-user reset returns the same generic success without invoking the sender. Preserve this native anti-enumeration behavior.
- **Verified in installed code:** signup/sign-in verification uses the same helper; explicit verification resend awaits its callback directly. Other verification branches also use the helper. The trial flag currently disables automatic signup/sign-in verification, not every explicit verification route.
- **Verified in project code:** the former SMTP catch replaced raw errors with MAIL_DELIVERY_FAILED and the project Better Auth logger retained severity only. The earlier runbook's suggestion to expect that503 from every reset request was incomplete: the native reset helper can swallow it. MAIL_UNAVAILABLE from the project pre-hook remains a separate configuration response.
- **Inference:** a transport/TLS/credential/sender failure, or an unknown/mistyped account, can explain browser success and an empty provider log. The exact previous hosted SMTP cause is not established by that symptom. Missing waitUntil is not evidence of cancellation here because the normal response awaits the send.
- **Platform rule, not observed hosted cause:** Workers may cancel work left outstanding after the response or client disconnect; `waitUntil` extends lifetime by up to30 seconds. If mail is deliberately moved into Better Auth background tasks later, wire the handler to the request's execution context and separately prove database-pool lifetime. The current request-scoped pool closes when app.fetch returns, so globally deferring native database tasks is inappropriate without another review. See [Workers context](https://developers.cloudflare.com/workers/runtime-apis/context/) and [Better Auth options](https://www.better-auth.com/docs/reference/options).

## Selected repair
Use the prepared native HTTP fallback, selected explicitly with `MAIL_TRANSPORT=resend_http` on the API Worker. Local/default `smtp` remains supported for compatibility and rollback. The existing complete mail configuration group is retained: SMTP_HOST,SMTP_USER,SMTP_PASSWORD,MAIL_FROM. The HTTP path uses SMTP_PASSWORD as the server-only Resend API key in its Authorization header; this is the same key already used by Resend SMTP, not a new secret copy. SMTP port/secure variables remain available for rollback. No credential is read from the deleted input file.

`sendResendMail` awaits one POST to the fixed `https://api.resend.com/emails`, with a15-second abort signal and redirects rejected. It sends the same sender, recipient, bilingual subject/text/escaped HTML and validated native auth link. Only a successful HTTP response with a nonempty message ID counts as provider acceptance. Error bodies are discarded; raw errors are never logged. There is no retry or automatic SMTP failover because ambiguous failures can otherwise duplicate messages. Provider acceptance is not mailbox delivery. See [Resend send-email reference](https://resend.com/docs/api-reference/emails/send-email).

This choice is an engineering decision: HTTP is locally verifiable inside workerd with all outbound traffic intercepted, while changing lifetime alone does not address the verified awaited path. It does not establish that SMTP is categorically unsupported by Workers.

## Safe diagnostics
- Hono generates an opaque request ID; caller-supplied X-Request-Id cannot inject private content. AsyncLocalStorage carries the same ID into native auth mail callbacks, and X-Request-Id is returned to the browser.
- Events: `auth_mail_attempt`, `auth_mail_accepted`, `auth_mail_failed`. Fields are requestId, kind (reset/verify), transport, and for failure a fixed errorClass plus finite code. No recipient, name, credential, token, link, provider ID, raw response, error message or stack is logged.
- HTTP codes appear as HTTP_401/403/429/5xx etc.; local failures are TIMEOUT, NETWORK_ERROR, INVALID_RESPONSE or INVALID_LINK. SMTP compatibility mode uses an allowlist of socket/auth codes, otherwise TRANSPORT_ERROR. HTTP403 alone does not distinguish restricted-key permission from sender/domain rejection; investigate the provider dashboard without logging its raw body.
- Correlate the reset POST's X-Request-Id with Worker events. `attempt` followed by `failed` proves callback/transport failure even if native HTTP status is200. `accepted` proves a provider response with an ID, not delivery. Absence of `attempt` can mean the callback was never invoked (including an unknown account); it does not independently prove why. Check complete log coverage before drawing conclusions.
